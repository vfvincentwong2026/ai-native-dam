01

客户怎么接入：两条路径

你是想 让 DAM 造一个新系统，还是想 把已经在跑的系统接进治理平面？两条路都有标准化流程，都不需要你去懂编译器和模型路由。

Path A · 造系统

我有一件重复性的运营工作

适合：运营团队、内容团队、任何想要一个内部小系统但不想排期开发的业务方
  1. 说人话提需求 —— 比如"每天扫一遍素材库，版权快到期提前 30 天提醒我"
  2. 审批规格书 —— 流水线把需求落成结构化 Spec（实体/字段/权限/工作流），你点头才算数
  3. 等一杯咖啡 —— 自动构建 + 沙箱真跑测试 + 13 项门禁，约 10 分钟
  4. 系统在你机器上跑起来 —— 一个标准 HTTP 服务，有自己的数据库和 API
看看拿到手的系统长什么样 →
Path B · 接治理

我已经有系统在跑，想被管起来

适合：已有内部工具/微服务的团队，需要登记、审计、健康监控和权限治理
  1. 写一个 manifest —— 仓库根目录放 dam.manifest.yaml，声明运行时/资源/数据边界
  2. 补齐 L1 四件事 —— 可声明打包、健康端点、零硬编码密钥（清单见下文）
  3. 走 MCP 登记流程 —— 写操作全部带审批闸门，幂等可重跑
  4. 出现在治理大屏 —— 注册、部署、健康心跳全留痕，随时可查
看 L1 接入清单和 manifest 模板 →
客户视角的一天： 早上提需求 → 审批规格 → 喝咖啡 → 系统上线 → 下午在大屏上看到它的健康心跳 → 三个月后审计时一键调出它的完整出身

04

已有系统接入：L1 清单 + 一个 manifest

1

可声明打包

Dockerfile、docker-compose 或 wrangler.toml 任一 —— 你的系统怎么被打包/启动，是声明出来的，不是口口相传的。

2

仓库根目录的 dam.manifest.yaml

声明运行时、资源下限、数据边界（哪些不出本机/哪些可上云/哪些必须脱敏）、健康端点。模板就在右边。

3

标准健康端点

GET /health 返回 200。DAM 的部署探针和心跳都靠它 —— 拒绝登记摸不到的系统。

4

零硬编码密钥

密钥只从环境变量读；需要 DAM 注入的密钥在 manifest 的 injectedSecrets 里声明。

# dam.manifest.yaml — InstallableUnit L1
apiVersion: dam.ai-native/v1
kind: InstallableUnit
metadata:
  name: my-system
  version: 1.0.0
spec:
  runtime:
    repo: https://github.com/you/my-system
    entrypoint: ["node", "src/server.ts"]
  resources:
    min: { cpu: 1, mem: 1Gi, storage: 5Gi }
  health:
    liveness: /health
  dataBoundary:
    localOnly: [客户数据]
    redacted:  [手机号, 身份证号]

登记走 MCP 工具流（起草 Spec → 提交 → 审批 → 注册 → 登记目标 → 登记实例 → 打心跳）， 写操作全部是两段式审批闸门，令牌一次性、有过期时间；脚本幂等可重跑。 完整指南：docs/onboarding.md。

05

背后发生了什么：六步流水线

Step 1 · Spec

规格审批

需求落成结构化 System Spec：实体、字段、权限、工作流。人工审批通过才进入下一步。

人类门禁
Step 2 · Blueprint

确定性编译

Spec 按固定规则编译成蓝图：技术栈、模块拆分、文件清单。无 LLM、无随机 —— 同 Spec 永远同哈希。

纯函数
Step 3 · Build

受控生成

C0–C3 分级路由到不同模型；服务端入口、契约、建表语句由编译器直出，不经 LLM。

预算熔断
Step 4 · Verify

门禁验证

13 项确定性检查 + 可执行沙箱：真实安装依赖、tsc 类型检查、跑测试。失败文件定点修复重试。

13 gates
Step 5 · Register

溯源注册

验证通过才允许注册。系统携带 spec id、blueprint hash、verify report —— 四级溯源链闭合。

verify-before-register
Step 6 · Deploy

受管部署

健康探针先活查再登记，target → instance → heartbeat 全程留痕，旧版本实例一键吊销。

拒绝幽灵部署
设计原则：LLM 只出现在"填充业务逻辑"这一个环节；凡是能确定性推导的 —— 依赖清单、tsconfig、 server 入口、数据库建表 —— 一律由编译器生成。模型的不确定性被压缩到最小面积。

07

你能得到什么

⛓

全链路可审计

每个线上系统都能回答：来自哪份需求、哪版蓝图、哪次验证、谁批准的。合规检查从"翻聊天记录"变成一次查询。

◎

模型可替换

模型分级路由 + 传输层抽象，OpenRouter / DeepSeek / 本地 Ollama 随时切换。供应商锁定不存在，成本自己说了算。

▣

失败可修复

沙箱真实跑 install/build/test，失败时从编译日志定位责任文件、带上下文定点重生成 —— 0.4.0 就是靠修复环自愈通过的。

◈

能力可沉淀

Skill 注册表 + 蒸馏队列：好用的生成模式回流入库，下一次编译直接复用。系统越用越聪明，而不是越用越乱。

08

客户常问

我不懂代码，能用吗？

路径 A 就是为不懂代码的人设计的：你用自然语言提需求，审批的是一份人可读的规格书，之后构建、验证、部署全自动。日常使用拿到的是标准 HTTP API；需要操作界面的话，可以让流水线再生成一个前端系统接上去。

生成的系统部署在哪？数据离开我的环境吗？

部署到你的环境：你的电脑、你的云账号、你的边缘节点，target 登记制。治理数据存本地 PGlite/SQLite，生成的系统默认 node:sqlite 零外部依赖。唯一出网的是 LLM 推理调用 —— 指向哪个端点由你配置，包括完全本地的 Ollama。已有系统接入时，数据边界在 manifest 里显式声明：什么不出本机、什么可上云、什么必须脱敏。

我已经有系统在跑了，接进来要改多少东西？

四件事：可声明打包（Dockerfile/compose/wrangler 任一）、根目录一个 dam.manifest.yaml、一个 /health 端点、密钥改为环境变量读取。全部改动发生在你自己的仓库，DAM 不动你的代码 —— 它只裁决、登记、审计。

必须用指定的大模型吗？

不需要。模型通过 C0–C3 分级路由接入，传输层可插拔：OpenRouter、DeepSeek、本地 Ollama 都已验证。换模型只改环境变量，治理链路和蓝图哈希完全不受影响。

生成的系统质量怎么保证？

三层：① 确定性文件（server 入口、契约、建表、tsconfig）不经过 LLM；② 13 项门禁 + 沙箱真实 install/build/test；③ 失败文件定点修复环。验证不过就不允许注册，注册不了就不存在部署。

出了问题怎么追溯？

每个系统携带四级溯源链：System → Run → Blueprint → Spec。大屏上点开任何一个实例，能一路回到当初那份审批过的需求规格 —— 包括哪次验证通过、谁批准的、跑在什么目标上。

现在是什么成熟度？

Founding Beta：六步流水线已端到端跑通真实系统（版权到期预警台 0.4.0 → 0.5.1），部署链闭环，三个真实 target 在线。沙箱目前是本机无隔离运行（dev-only），Docker 隔离沙箱在 ADR 0010 路线图内。
